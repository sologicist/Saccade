## Confirmed PDF selection

Automatic BusinessRun.prepare now requires a current native download operation
and the exact confirmed (absolute path, SHA-256) association. An existing file
that passes filesystem checks without this association is rejected with
chrome_confirmed_download_required. Another name/path, modified content, an
incomplete file or an old operation cannot substitute for the confirmed PDF.

Every native click/hold-click starts a new operation before dispatch and clears
the earlier association and tickets. Failed observations revoke the operation;
late answers cannot revive it. A new deliberate operation is required after a
terminal failure. not_observed and in_progress remain pending, allowing a late
completion without another click. Switching away from the operation's tab,
debugger detachment or losing the transport fails closed. Consequently, another
ordinary click also invalidates an earlier PDF; analysis should follow its
completed download without another browser click.

The existing worker envelope carries the host-verified path/hash, not a PR5
receipt. The worker reconstructs only that association and revalidates it during
prepare. AccountingContext also compares the exact bytes it passes to the
provider against that hash, closing a replacement window between worker checks
and provider input. Client registration, direction, full reference loading,
file-size/signature/stability checks and strict output validation remain in place.
Pre-existing user-selected PDFs are not implicitly enabled by this download path.

## Label-independent Chrome observation

The existing tools.js observes Chrome metadata for every native click, including
icon-only, PDF, Exporter, menu and unlabeled controls. It never examines the
button label to enable download observation. Double-click and hold-click use
the same underlying trusted input path. No extra download permission is granted.

One bounded metadata observation lives on the existing agent line. downloads
onCreated supplies a fresh download ID; onChanged records interruption or file
loss. webRequest onBeforeRequest/onBeforeRedirect/onHeadersReceived establish
the requesting tab and redirect chain, without reading headers or bodies. Both
the DownloadItem initial and final URL must match exactly one observed request
chain belonging to the clicked, still-owned tab. Competing matching requests in
another tab, or requests already in flight before the click, cannot establish
authority. A referrer or filename alone is never used as proof. Redirects with
a different referrer can succeed when this request-chain evidence is complete.

Only IDs delivered by onCreated are queried with downloads.search({id}); no
recent-history filename search or guessed path is used. Multiple candidate IDs
fail as ambiguous. The native operation ID is generated by the controller,
cannot be supplied in model tool arguments, and is checked before association.
The absolute path and operation ID are stripped before tool results reach the
model. Custom Chrome download destinations remain supported.

An ordinary click pays a 100 ms grace, without eight-second polling. Status is
rechecked at existing action/settle/business boundaries. Each metadata lookup is
capped at 500 ms; the native status request is capped at two seconds. A pending
download tells the agent to wait rather than repeat the click. Normal Web input,
keyboard, scrolling, tabs, scripts, scraping and dialogs retain their existing
controller/ownership checks. No UI or execution selector is added or changed.

Chrome API constraints were checked against the official
[downloads documentation](https://developer.chrome.com/docs/extensions/reference/api/downloads)
and [webRequest documentation](https://developer.chrome.com/docs/extensions/reference/api/webRequest).
DownloadItem does not supply a tab identity, which is why referrer equality alone
has been replaced with tab-bound request correlation.
